Traditional Governance, Risk, and Compliance (GRC) workflows rely heavily on manual artifact collection, static spreadsheets, and point-in-time annual audits. This creates massive lag between infrastructure drift and risk detection.

I created an implementation of Compliance-as-Code, which can be found <a href="https://github.com/informed-operator/my-grc-policy-engine" target="_blank">here</a>. It automates control validation for ISO 27001:2022 Annex A Technological Controls in two distinct areas:

Continuous Posture Monitoring: Python telemetry collectors querying live GitHub repository metadata and determining if it complies with OPA Rego rules.

![Posture Monitoring](/assets/images/posture-monitoring.png "Posture Monitoring")

Pre-Deployment Shift-Left Guardrails: Intercepting Terraform execution plans in CI/CD to block non-compliant infrastructure before provisioning.

![IAC Guardrails](/assets/images/iac-guardrails.png "IAC Guardrails")

## Core Components

1. Telemetry Ingestion & API Posture Checking
Instead of trusting self-reported documentation (which can become outdated), the engine pulls live metadata from target repositories via the GitHub REST API (evaluating branch protections, required reviews, SAST, dependency scanning, and security policies). A Python-based collector normalizes target state of one or more repositories into structured JSON payloads (input.json).  As of now, this repository, called `my-grc-policy-engine`, runs checks both on itself and `grc-test-target-failing` to contrast a hardened repository and a repository that is far less hardened.  Data collection and policy evaluation are separate so rules remain pure, stateless, and testable.

2. Policy-as-Code Rules (OPA / Rego v1)
Compliance rules are written as declarative code rather than subjective guidelines. The engine maps findings directly to ISO 27001:2022 controls:

  - Control A.8.28 (Secure Coding): Validates that default branches are protected, require code reviews, enforce SAST (CodeQL), integrate dependency scanning (Dependabot), and maintain a documented SECURITY.md baseline.

  - Control A.8.24 (Use of Cryptography): Validates that proposed Infrastructure as Code (Terraform) enforces server-side encryption (AES256/KMS) on cloud data stores.

3. Pre-Deployment Shift-Left Guardrails
To prevent misconfigurations from ever reaching production, the repository includes a GitHub Actions pull request check that:

    1. Generates an offline simulation plan (terraform plan -out=tfplan) using mock-validated provider settings.

    2. Exports the plan to structured JSON (terraform show -json tfplan).

    3. Evaluates the plan against OPA Rego policies.

    4. Automatically halts the pipeline (exit 1) if unencrypted resources or security gaps are detected before terraform apply can execute.

## Local Verification & Usage

You can run the audit engine and evaluate OPA policies on your machine.  First, clone the linked <a href="https://github.com/informed-operator/my-grc-policy-engine"  target="_blank">repository</a> onto your machine.  Open a Bash shell.  You will want to set the value of two variables, a GitHub token and the target repositories.

```
# 1. Export target configuration and token
export GITHUB_TOKEN="ghp_YOUR_TOKEN_HERE"
export TARGET_REPOS="informed-operator/my-grc-policy-engine,informed-operator/grc-test-target-failing"
```

Now you are ready to run the collector which will gather information on the state of the repositories and write it to a JSON file.

```
# 2. Run telemetry collection
python collectors/github_collector.py
```

Finally, you can now use the repository information in `input.json` to determine the compliance or lack thereof with various policy rules

```
# 3. Evaluate OPA policy rules locally
opa eval --data policies/ --input input.json "data.iso27001.a8_28.violations" --format prett
```

Any violations will be displayed in a JSON object in your terminal.
